# Workflows and HR rules

Approval routes are **configuration** (Administration → Workflows), not code.
Where a PRC-specific rule is unknown, the system makes it configurable and the
assumption is listed in §6 — nothing here is a statement of agency policy.

## 1. The engine

Three kinds of request share one engine: **leave applications**, **attendance
corrections** and **HR service requests**. Each has:

* a **workflow** (`workflows`) — chosen when the draft is created: the leave
  type's or request type's own workflow if set, otherwise the default for that
  kind;
* ordered **steps** (`workflow_steps`) each acted on by either
  * `supervisor` — the requester's immediate supervisor, or the head of the
    requester's unit/any parent unit (and the person must hold `team.view`), or
  * `permission` — anyone holding the step's permission;
* a **status**: `draft → in_review → approved → completed`, or `rejected` /
  `cancelled`. The status a step produces on approval (`in_review`,
  `approved`, `completed`) is part of the step definition.

All transitions run inside database functions (`wf_submit`, `wf_act`, …):

| Action | Who | Effect |
|---|---|---|
| Submit | the requester, on their own draft | validates (see below), moves to step 1, notifies the people who must act |
| Approve | whoever the current step names; **never the requester** | next step, or the step's final status; notifies requester and next actors |
| Reject | same; remarks required | terminal `rejected` |
| Return | same; remarks required | back to `draft` for revision |
| Cancel | the requester (or `workflow.override`) while the request is **open** | `cancelled`. A request whose last step has been approved is final and cannot be cancelled |
| Comment | anyone who can see the request | timeline entry; notifies the requester |

Clients cannot write `status`, `current_step_order`, `workflow_code`,
`request_no`, `submitted_at`, `completed_at`, `assigned_to` or
`result_document_id` directly (a trigger refuses it).

**Missing supervisor.** If an employee has no supervisor on record, a holder of
`workflow.override` (HR admin) may act on supervisor steps so requests never
stall; `workflow.override` holders are notified that no supervisor exists. If a
supervisor *does* exist, HR cannot bypass them.

**Request numbers**: `HR-2026-000123`, `LV-…`, `AC-…` (year in Manila time;
generated by the database).

## 2. Default workflows (editable)

### Attendance correction — `ATTENDANCE_CORRECTION_DEFAULT`

| # | Status label | Acted by | On approve |
|---|---|---|---|
| 1 | For Supervisor Review | supervisor | status **Approved**, moves to step 2 |
| 2 | For HR Finalization | `attendance.write` | **Completed** — the DTR for that day is updated (time in/out; status becomes `PRESENT` when both times exist; source `correction`) |

The employee sees "Approved" after step 1 and "Approved · DTR updated" when HR
finalizes. Employee flow: Draft → Submitted → For Supervisor Review → Approved
(or Rejected) → HR finalizes. Validation on submit: reason required, date not in
the future, the corrected time(s) must be provided for the chosen type; one open
request per date and type. Late/undertime are **not** computed (no work schedule
is assumed) — those statuses come from the source of the record.

### Leave — `LEAVE_DEFAULT`

| # | Status label | Acted by | On approve |
|---|---|---|---|
| 1 | For Supervisor Approval | supervisor | In review |
| 2 | For HR Processing | `leave.manage` | **Approved** (final) — used days are added to the balance if the type deducts |

Validation on submit: leave type active; no overlap with the employee's other
pending/approved leave; if the type **requires a balance**, days must not exceed
`beginning + earned − used − pending` for that year. Days default to Mon–Fri
excluding configured holidays; a half-day can be entered (0.5). Balances are
maintained by HR (Leave → Maintain balance). **No entitlement or accrual is
computed**; the leave type's `accrual_rule` field is reserved documentation for a
future accrual job.

### HR service request — `HR_REQUEST_DEFAULT`

| # | Status label | Acted by | On approve |
|---|---|---|---|
| 1 | Received / Under Review | `request.process` | In review |
| 2 | For Approval | `request.approve` | **Approved** |
| 3 | For Release | `request.process` | **Completed** (Released) |

Request types can require an attachment before submission (e.g. PDS update) and/or
**produce a document**: HR must upload the generated file to the employee's folder
and link it to the request before step 3 can be approved; the requester then sees
and downloads it from the request page. HR can assign a request to a staff member.
Request types are administered in Administration → HR request types.

The timeline on every request page shows each action with date, time, user and
remarks, plus a progress tracker built from the configured steps.

## 3. Changing a workflow

Administration → Workflows lets a Super Administrator add, edit and remove steps,
choose the actor (supervisor or a permission) and the status after approval, and
deactivate a workflow. Requests **already in progress follow the live
definition**, so avoid renumbering or deleting a step that has requests waiting
on it (the page shows how many are in progress).

## 4. Profile completion

The percentage on the dashboard is the share of these checks that pass (an
explicit, documented assumption — revise by replacing `profile_completion()`):

name & sex · date and place of birth · civil status & citizenship · mobile &
personal email · residential address · TIN, GSIS, PhilHealth and Pag-IBIG numbers ·
family background · educational background · three character references · at
least one personnel document · PDS certified.

## 5. PDS certification

The employee certifies the electronic PDS (an append-only event), HR verifies or
returns it with remarks. The generated PDF is an **electronic summary**, not the
official CSC Form 212, until validated and signed under agency procedures.

## 6. Assumptions requiring agency validation

* Default role mapping and permission set; who may approve what.
* Default workflow steps and the status labels shown to employees.
* Leave types seeded (names only), `requires_balance` defaults, working-day
  counting (Mon–Fri minus holidays), no accrual rules.
* Government ID formats (loose), salary grade/step ranges.
* Which document categories are **required** (seed: Appointment Papers and PDS).
* PDS declaration question wording and the PDS field list vs. the current CSC form.
* Whether supervisors may see more than attendance, leave and request information.
* Profile-completion checklist (§4) and the "service milestone" interval (5 years).
